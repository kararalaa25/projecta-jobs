# Projecta Jobs — architecture, product and security audit

Date: 30 October 2026, Asia/Baghdad. Baseline: `fd78adf` on main. The changes accompanying this audit are **local review changes only**: no commits, pushes, production migrations/uploads, ingestion reruns or deployments were performed. Follow-up local staging uploads use synthetic data only; see the staging acceptance report.

## Executive assessment

The existing React/Vite + Vercel API + Supabase architecture is appropriate for this marketplace's present size. Replacing it with a new framework or microservices would add risk without addressing the main problems. The immediate priorities are private resume handling, data consistency, narrower data exposure and release/observability controls.

The two public APIs currently return 200 and there are 867 active records. This is not equivalent to 867 verified, complete job offers: 599 are explicitly unparsed Telegram posts. Guaranteed “zero 502 errors” is not a credible promise for a networked system with external dependencies. The appropriate target is zero known reproducible defects, bounded requests, correct failure semantics, monitored availability and recovery—not converting failures into fake successful responses.

## 502 diagnosis and operational health

The previous reproducible failure was `PGRST125`: a copied Supabase API URL already included `/rest/v1`, and the SDK appended it again. The root normalization in `config/supabase-url.js` is covered by regression tests and must remain shared by browser/server clients.

Other plausible causes are distinct and must be measured rather than assumed:

- Missing or malformed Vercel environment variables, a service key belonging to a different project, or cloud-only values never copied into Vercel Production.
- Missing tables/columns/RPCs or schema-cache refresh after a migration (`PGRST204/205/202`, `42703`).
- Incorrect grants/RLS (`42501`); private tables intentionally cannot use the public key as a privilege fallback.
- DNS/TLS/connectivity failures, timeouts, upstream maintenance, quota exhaustion or Vercel function duration limits.
- Unsupported runtime/dependency versions, malformed query paths and unbounded admin scans.

Recommended acceptance/monitoring: public GET smoke checks on deployment, schema contract tests before rollout, per-route request/latency/error metrics with safe request IDs, separate alerts for configuration/schema/transport issues, and a monthly availability objective agreed with the owner. Consider a 99.9% GET availability objective as a proposal, not an achieved SLA. Retry only safe reads within the request budget; do not blindly retry application/job writes. Keep expected 400/401/403/404/409/413/429 responses distinct from genuine upstream 502/503 failures.

## Authorization assessment

The trusted logic in `config/access.js` grants owner powers only to the two confirmed emails. Server handlers fetch identity from Supabase for each privileged request; user-editable `user_metadata` and client-provided roles do not authorize administration. Owners bypass the medical-verification modal through the same `canPublish` rule used by the publishing API. Suspended users are denied. The existing tests cover both owners, unconfirmed lookalikes, forged metadata, ordinary users, protected owner accounts and suspension expiry.

Live account confirmation was verified read-only. No owner impersonation, password reset, email/SMS or live sign-in was performed, so this is not a claim that a real owner session completed every admin write during the audit. MFA for super-admin sessions, rate limits on administrative actions and durable audit monitoring are recommended as a separate security rollout.

## Architecture to retain and changes requiring approval

Retain React/Vite, Vercel routes, Supabase Auth/Postgres/Storage and the current Telegram/Gemini pipeline. Prepare small modules rather than a framework rewrite.

Approval is needed for private resume storage/schema activation (008), the sixth production category (009), removal of direct listing reads (010), any live backfill/moderation changes, retention/cleanup policy and the final deployment. Server-side search/cursors, an asynchronous AV pipeline, moderation schema separation and MFA enforcement are recommendations, not changes secretly activated in this branch.

See `implementation-review.md` for the precise prepared implementation, activation order, validation evidence and remaining acceptance work.
